# Release Notes

The text customers read on Google Play and the App Store is generated by
`scripts/release-notes.mjs` (logic in `scripts/lib/release-notes.mjs`, tests in
`scripts/lib/__tests__/release-notes.test.mjs`).

## Write the wording yourself, on ONE line, in the commit

This is the primary path and it is worth using on anything a customer would
actually notice. Put a `Release-Note:` trailer in the commit **body**, and keep
the whole note **on a single line**. That is not a style preference: git reads a
trailer as one line, and so does the generator.

```
fix(cash-floor): month 0 gets the same $2 cushion as every other month

The first forecast month was the only one drained to exactly its floor.

Release-Note: Your first forecast month keeps the same safety cushion as every month after it.
```

From the command line, same thing, one line:

```bash
git commit -m "fix(cash-floor): month 0 gets the same \$2 cushion as every other month" \
           -m "Release-Note: Your first forecast month keeps the same safety cushion as every month after it."
```

- It is published **verbatim**, and it beats anything the generator would
  otherwise derive.
- Several commits in one release each contribute their line, newest first, up to
  five.
- `Release-Note: none` says "this commit adds nothing to the listing" out loud.
- It works on any commit type. A `chore:` you decide is worth announcing gets
  announced.
- A short note is never thrown away. If it is under the 20-byte minimum the store
  needs, it is padded **underneath** with the release's own derived lines. Your
  words stay first and stay intact.

### If it really has to wrap: indent the continuation

The line can be as long as you like, so the simple answer is not to wrap it. If
your editor or your review style forces a wrap, **indent** the continuation by a
space or a tab and it is folded back into one value, exactly the way
`git interpret-trailers` folds a trailer:

```
Release-Note: Your first forecast month keeps the same safety cushion
  as every month after it.
```

An **unindented** second line is not part of the trailer, in git or here. The
generator publishes what it got and prints a warning naming the half it dropped:

```
release-notes: Release-Note: looks wrapped onto the next line, and git does not
read it that way. Published: "...". DROPPED: "...".
```

That warning goes to stderr, so it lands in the workflow log for the run that
published the note. It was added on 2026-08-22 because the example in this very
file used to be wrapped, and the note it produced was silently cut in half.

Why a trailer rather than a file: it costs one line at the moment the commit is
already being written, it travels with the change through cherry-picks and
reverts, there is no second file to keep in sync, and it **cannot go stale** —
it only ever applies to the release that contains its commit.

### Writing a good one

Write for somebody who opened a budgeting app, not for the next engineer.

| Instead of | Write |
| --- | --- |
| The $2 above the floor is the cushion, not surplus the cards could not absorb | Your forecast keeps a small safety cushion every month, including the first |
| One floor, judged in cents, in one place | Cash-flow warnings now agree with the numbers in the table |
| Read the real cards and plans, and price the no-loan plan | See what paying your cards off without a loan would cost you |

Never promise something that did not ship. A vague-but-true line is fine; an
overstated one is not.

## Hand-writing a whole release

Put the finished lines, one per line, in **`docs/next-release-notes.txt`**. It
overrides both the trailers and the derived text.

It is honoured **only when a commit in the same release actually changed that
file**. That is deliberate: without the check, a file written for 6.4 and then
forgotten would keep republishing itself on 6.5, 6.6 and 6.7. With it, editing
the file opts one release in and doing nothing opts every later release out.

## What happens if you write nothing

The generator falls back, in order:

1. **Themed sentences it wrote itself.** Each public commit (`feat`, `fix`,
   `perf`, non-internal scope, no engineering vocabulary) is classified into an
   area — forecast, credit card payoff, bank connections, accounts, bills,
   goals, budget, transactions, vehicles and loans, sign-in, charts,
   performance — and the area's pre-written sentence is published. **The commit
   subject itself is never published.** That is the change made on 2026-08-22:
   the old script only ever *rejected* subjects, so anything well-written enough
   to survive its filters went to the store verbatim, which is how
   "The $2 above the floor is the cushion…" ended up on the live 6.4.0 listing.
2. **A generic line** when public work landed in an area with no theme:
   `Bug fixes and small improvements across the app.`
3. **A maintenance line** when nothing user-visible shipped at all:
   `Maintenance release. Nothing changes in how you use Forgenta this time. This one is quiet work behind the scenes to keep things steady.`

   It reaches a customer only when there is no human wording anywhere in the
   range. A `Release-Note:` trailer, however short, always outranks it.

The last one is the honest answer for a docs-and-chores release. It replaced an
evergreen paragraph that promised "performance improvements, stability fixes" on
releases containing neither.

## Where it is used

- **Google Play, automatic.** `.github/workflows/android-build.yml`, step
  *"Generate release notes from this push's commits"*, writes
  `whatsnew/whatsnew-en-US` and **fails the build** unless `wc -c` measures it at
  **20 to 500 bytes** (500 is Google Play's own per-locale cap).

  The generator's own ceiling is **480 bytes**, not 500: it is an internal cap
  that leaves 20 bytes of headroom under the gate rather than sitting on it. So
  the numbers are 20..480 produced, inside 20..500 enforced. They are different
  numbers and both are in `scripts/lib/release-notes.mjs` as `MAX_TOTAL_BYTES`
  and in the workflow's own check. See the byte-cap tests.
- **App Store, manual paste.** `.github/workflows/ios-build.yml`, step
  *"Customer release note (paste into App Store Connect)"*, prints the same text
  to the run summary. `xcrun altool --upload-app` sends the binary only and
  cannot set "What's New"; doing that automatically needs an App Store Connect
  API client this repo does not have.

## Running it locally

```bash
node scripts/release-notes.mjs HEAD~10..HEAD --why   # --why explains the source on stderr
git log --format=%s | node scripts/release-notes.mjs --stdin
npx vitest run scripts/lib/__tests__/release-notes.test.mjs --reporter=dot
```

`scripts/release-notes.sh` still works; it is a shim that forwards to the above.
